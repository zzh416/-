# P4 交付计划

目标：把已完成 P3 功能整理为可在本机稳定运行、可备份恢复、可诊断且有明确安全边界的版本。

## 交付门槛

- [x] P4-1：请求具备关联 ID、安全响应头和不含私密正文的结构化访问日志。
- [x] P4-2：一条命令备份 PostgreSQL 与 `data/`，校验清单后可恢复；恢复前自动生成安全备份。
- [x] P4-3：在隔离数据库中完成 5,000 题、20,000 来源块的性能基准，输出可复现报告。
- [x] P4-4：Compose 默认运行形态移除热更新和源码挂载，容器使用最小权限并通过重启、持久化检查。
- [x] P4-5：依赖、安全、完整回归与安装文档通过，P3/P4 状态文档与实际实现一致。

## 执行顺序

1. 固化 P4 范围并补齐 API 运行诊断与安全回归。
2. 实现备份、校验、恢复脚本，并在独立临时数据库/目录演练。
3. 编写和运行隔离性能基准，按证据优化查询或记录容量边界。
4. 收紧 Compose 发布运行方式，验证构建、健康、重启和数据持久化。
5. 运行完整测试与依赖审计，更新 README、启动步骤、架构和验收记录。

## 明确边界

- 当前仍是本机单用户应用，只绑定 `127.0.0.1`；开放到局域网或公网前必须增加身份认证和 HTTPS。
- Redis 只承载任务队列，不作为唯一业务数据备份对象。
- API Key 不进入备份、日志、Git 或验收报告。
- AI 生成缺失答案属于下一版本，不纳入 P4。
