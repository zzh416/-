# P1 实施计划：文字资料、问答与备注

状态：P1 已实施并验收。日期：2026-10-20。

## 目标

在现有可运行骨架上完成：**资料库 → 文字导入 → 手动整理问答 → 关键词搜索 → 问答阅读 → 个人备注 → 持久化保存**。

本计划已按现有架构文档的 P1 范围执行。基础检查见 `docs/P1前架构检查.md`，完成证据见 `docs/P1验收记录.md`。

## 当前可复用的部分

- React、Ant Design、TanStack Query 与 Vite 代理。
- FastAPI 入口、Pydantic Settings、SQLAlchemy 会话基础。
- PostgreSQL/Redis 数据卷与 API/Worker 共用 data 目录。
- 已能完成 echo 任务的 Celery Worker；P1 不为简单同步操作强制使用队列。
- 已确定的云模型配置方向，保持不变；P1 的基本流程不要求模型 Key。

## 实施原则

1. 先修本地访问范围、数据库 URL 组装和就绪检查，再写入私有业务资料。
2. 只建立 P1 必需的数据，保留 owner、来源和版本，不建设完整推荐系统。
3. 用少量完整使用流程推进，不能把所有表、所有接口、所有页面各做一遍后再联调。
4. 模型生成、OCR、向量库不成为 P1 的外部依赖。
5. 改动通过测试再进入下一个阶段，不用当前两个冒烟测试代替业务验收。

## P1 数据范围

按功能迁移建立：本地用户、资料库、资料及原文版本、文本块、问题及出现记录、答案及版本、个人备注、创建请求幂等记录。共享的 owner、时间戳和版本约定先统一。

原件和原始输入保持可追溯；资料修改新增版本。手工题可以没有资料来源，但标明“用户手写”。原材料只有题目时不能创建虚构答案。备注归属用户，独立于答案正文。

个人版后台使用固定本地用户上下文，不能从客户端提交的 ownerId 决定读写权限。数据结构保留多人使用所需的 owner_id；这并不等于已经实现多人登录。

不在 P1 建立技能图谱、推荐运行记录、embedding 或模型计费表。

## 接口与导入方式

沿用 `/api/v1`、JSON 请求/响应、统一错误与 OpenAPI 类型。先定义资料库、资料、题目、答案、备注的合约，前后端依据同一合约实现。

文字导入只处理有大小上限的纯文本、TXT 和 Markdown，不调用模型。建议上限先设为 1 MiB 并配置化，支持 UTF-8/带 BOM 的 UTF-8；其他编码明确提示转换，不用错误编码静默解码。

对于该轻量路径，可在一次事务中完成文本保存和简单分段。实施时应统一导入合约：同步完成返回 201 和 READY 状态；以后异步导入返回 202、PROCESSING 与 jobId。前端按明确的状态联合类型处理，两类返回从首次定义合约时就说明。总体文档原本只列 202，这属于 P1 建议的细化，需要在实施该接口时同步文档与 Schema。

如果实现时仍决定保持纯异步导入，则必须同时实现数据库任务状态及可靠投递，不能只调用 `.delay()` 后假定任务一定完成。二者择一，不维护两套业务保存逻辑。

知识库管理在 P1 指资料库与知识文本的新增、查看、修订、删除；搜索采用有分页和大小限制的关键词匹配。先满足中文子串与英文技术词的基本可用性，后续再引入分词和混合检索。

### 检查点一：资料可以可靠保存

完成 T01–T07 后，能够从浏览器创建资料库，导入文字/TXT/Markdown，查看来源文字；刷新仍可读取，非法输入有明确提示。数据库迁移可在测试空库重放。

### 检查点二：问答与笔记可用

完成 T08–T11 后，能够手动建题、填写/编辑答案、查看出处、搜索并写备注。问题和答案字体不同，代码使用等宽字体；危险内容不能作为 HTML 或脚本执行。

### 检查点三：P1 交付

完成 T12–T13 后，重复创建不重复保存，版本冲突不覆盖更新，删除遵循已说明的来源规则，限定 owner 的读写检查通过。重启后的持久化用独立验收数据验证，不执行 `down -v`。

## 测试策略

- 规则和服务测试覆盖：输入上限、空题干、无答案、未知 ID、owner 越权、并发编辑、重复提交和删除行为。
- 数据库迁移测试使用独立测试库，不删除或重置开发库。
- API 集成测试贯通创建、读取、更新、搜索和删除，检查真实持久化与返回合约。
- 前端验证加载、失败、空状态、重复点击和保存反馈，检查 Markdown 禁用原始 HTML、图片自动加载及危险链接。
- Playwright 验证“创建资料库 → 导入 → 建题 → 编辑答案 → 写备注 → 搜索 → 刷新”的完整流程及窄屏阅读。
- 每个功能先跑对应的聚焦测试，阶段结束再跑已有后端测试、前端 lint/build 与完整流程。

现有命令（在项目根目录）：

```powershell
docker compose -f infra/docker-compose.yml exec -T api python -m pytest -q
docker compose -f infra/docker-compose.yml exec -T web npm run lint
docker compose -f infra/docker-compose.yml exec -T web npm run build
```

新增业务测试文件、迁移命令和端到端脚本随任务写入项目，不能在尚未实现时宣称其已通过。

## 并行安排

基础配置检查与依赖固定可分别推进。资料、问答、备注的接口合约明确后，可以并行开发前端页面和对应后端服务。数据库迁移顺序、共享 Schema 和主路由装配由一个负责人协调，避免同时修改同一文件。

## 风险与控制

| 风险 | 控制 |
| --- | --- |
| 为未来功能提前实现全部架构 | P1 只交付文字与手动整理，不引入模型和向量依赖 |
| 只实现 UI，数据仍在浏览器内存 | 每个使用流程必须连接真实数据库，检查刷新后保存 |
| 导入覆盖原文或人工答案 | 原文与答案版本化，编辑使用 expectedVersion |
| 文件后缀伪装或 Markdown 执行脚本 | 限制文件类型/体积/编码，按不可信文本安全呈现 |
| 依赖更新导致容器使用旧包 | 固定依赖并明确 Web 匿名卷刷新方式 |
| 验收误清理用户数据库 | 使用独立测试库，禁止用清空数据卷替代测试隔离 |

P1 的完成标准是这条使用流程可稳定重复完成，而不是目录、接口名称或空页面已经齐全。
