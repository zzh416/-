## 需要在 P1 开始时处理的问题

### R1：先落实仅本机访问边界

位置：`infra/docker-compose.yml:58`、`:106`。

API/Web 当前端口映射为 `9000:9000` 和 `5173:5173`。实际运行状态也显示绑定 `0.0.0.0` 和 IPv6 全接口，范围大于设计文档已确定的 localhost 单用户。

当前只存在健康接口；一旦 P1 增加资料读写，这个配置就会使私有接口监听在非回环地址，能否从其他设备访问还取决于主机防火墙和网络。CORS 不承担鉴权职责。

处理建议：改成 `127.0.0.1:9000:9000`、`127.0.0.1:5173:5173`，并实现本地模式的 Host/Origin 校验。后端统一获取本地用户，所有业务查询限制 owner，客户端不能指定任意 owner。以后开放远程访问时单独补完整认证。

Docker 官方说明了端口发布及主机地址设置：[Compose ports](https://docs.docker.com/reference/compose-file/services/#ports)。

### R2：数据库密码不能直接拼入 URI

位置：`infra/docker-compose.yml:41`、`:72`，以及 `backend/app/db.py:7`。

Compose 将 `POSTGRES_PASSWORD` 原样拼接到 `DATABASE_URL`。使用虚构密码 `demo@value` 做纯内存验证，SQLAlchemy 解析出的主机为 `value@postgres`，而非 `postgres`。用户更换为包含 URI 保留字符的密码后，API 和 Worker 可能无法连接数据库。

处理建议：分别传递主机、端口、数据库名、用户名、密码，在 Python 中用 SQLAlchemy `URL.create()` 组装连接对象；如果保留完整 URL 配置入口，明确其优先级并要求调用方提供合法编码。增加包含 `@`、`:`、`/`、`#` 等字符的配置测试，日志不输出密码。

### R3：区分“进程存活”与“业务就绪”

位置：`backend/app/routes/health.py:31`、`backend/tests/test_health.py:15`。

当前依赖检查失败时，明细会记录错误，但接口仍返回 HTTP 200 和顶层 `status: ok`。用依赖替换和 mock 在独立测试进程中模拟数据库/Redis 故障，已确认这一行为；没有中断真实数据库或 Redis。

建议保留简单的存活接口，另外提供有明确超时的就绪接口：依赖可用时返回 200；必要依赖不可用时返回 503/degraded，并对失败分支写测试。检查中使用的 Redis 客户端应妥善释放，连接和读取都设置超时。

这不代表当前数据库有故障；当前实际连通检查均通过。

### R4：明确前端依赖卷的更新方式

位置：`infra/docker-compose.yml:104`，以及 `README.md:29`。

`/app/node_modules` 使用匿名卷，而 README 只说明 `up -d --build`。容器重建时可能复用已有匿名卷，导致新镜像里的依赖被旧卷覆盖。P1 新增包后可能出现“构建镜像成功，但运行时找不到包”。

建议使用明确的依赖同步策略，或只重建 web 的匿名依赖卷，例如在完成镜像构建后针对 web 使用 `--renew-anon-volumes`；不要通过 `down -v` 一并删除 PostgreSQL 的数据卷。前端镜像安装依赖改用与锁文件一致的 `npm ci`。

此项是后续更新时的风险，不是当前构建失败。[Docker Compose up 参数说明](https://docs.docker.com/reference/cli/docker/compose/up/)。
